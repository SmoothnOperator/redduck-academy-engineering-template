# Solution

## Language

language: "typescript"

## What was the problem

In the original design, `UserStore` held the complete `UserRecord` (`username`, `role`, and `passwordHash`) and combined high-trust authentication logic with convenience queries. Specifically, it exposed a `getUser(username)` method that returned the raw internal `UserRecord` containing `passwordHash`. On top of that, convenience reporting (`report()`) constructed its rows by iterating usernames and calling `this.getUser(name)`. Because `getUser` handed out the full record, every row generated by `report()` embedded the raw password hash (`${user.username} (${user.role}) ${user.passwordHash}`). As a result, any ordinary caller requesting a report or looking up user metadata received every user's secret password hash without needing an exploit or privilege escalation. The high-trust secret state was directly connected to convenience features.

## The split

We applied the core and periphery pattern by separating the high-trust security boundary from low-trust convenience features:

1. **The Core (`UserStore`)**: Holds the sensitive state (`users: Record<string, UserRecord>`) and keeps the password hashes strictly encapsulated in private scope. It exposes only a minimal, narrow interface:
   - `verify(username, password): boolean` — verifies credentials and returns strictly a boolean without exposing the hash itself.
   - `getProfile(username): PublicProfile | undefined` — returns only non-sensitive public identity data (`{ username, role }`).
   - The core refuses to return `UserRecord` or any reference to `passwordHash`.
2. **The Periphery (`report`)**: Rebuilt strictly on top of the narrow public interface (`getProfile`). It iterates over user profiles and formats the rows (`${profile.username} (${profile.role})`). Because the periphery only consumes `PublicProfile`, it has no capability or mechanism to observe, leak, or handle password hashes.

## Removal versus guarding

- **Guarding** keeps the path to the secret accessible in the public interface but places a conditional check in front of it (for example, checking caller permissions like `if (caller.isAdmin) return record.passwordHash` or adding a parameter flag). A guarded path remains a continuous attack surface: any oversight, permission bug, misconfiguration, or caller bypass immediately leaks the secret.
- **Removal (our split)** deletes the path to the secret entirely from the public contract. No method on `UserStore` returns a `UserRecord` or `passwordHash`.

Removing the condition is fundamentally stronger because the vulnerability cannot even be formulated or called. A path that no longer exists requires zero ongoing maintenance, cannot be bypassed, and cannot be accidentally compromised by future periphery additions.
